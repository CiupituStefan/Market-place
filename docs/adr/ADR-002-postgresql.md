# ADR-002: PostgreSQL with Drizzle ORM, one database per service

- Status: Accepted
- Date: 2026-10-05

## Context

Every service needs transactional storage. Orders, payments and inventory require strong
consistency, row-level locking and constraints; the catalog needs flexible attributes and search.

## Decision

- **PostgreSQL 16** for every service (Amazon RDS in production), one database and role per service.
- **Drizzle ORM** with SQL migrations generated by drizzle-kit and committed to the repository.
- Integration tests on **PGlite** (in-process Postgres) with the real migrations.

## Alternatives considered

- **Prisma**: excellent DX, but a separate query engine binary, weaker control over SQL (locking
  clauses, partial indexes) and heavier ESM/monorepo setup.
- **TypeORM**: decorator entities mirror Nest style, but migrations and typing are less reliable.
- **Raw SQL (`pg`)**: maximum control, no type safety for result rows.
- **DynamoDB / MongoDB**: weaker fit for relational, transactional commerce data.

## Consequences

- Typed queries close to SQL; locking (`FOR UPDATE`), partial indexes and CTEs are first-class.
- Migrations are plain SQL reviewed in pull requests and applied by a pre-deploy Job.
- PGlite is single-connection: tests that need concurrent connections use a real PostgreSQL.
